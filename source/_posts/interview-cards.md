## 一、速记卡

| 术语 | 一句话答案 |
|---|---|
| `async def` vs `def` 路由 | `def` 被丢线程池；`async def` 在事件循环里跑。阻塞 SDK 用 `def`，异步 IO 用 `async def` |
| `Depends` 缓存 | 同一请求内，同一依赖只执行一次，结果被复用 |
| `yield` 依赖 | 清理逻辑在**响应发送之后**执行 |
| `Annotated[X, Depends(...)]` | 保留类型推导、可复用别名、可被 `dependency_overrides` 覆盖 |
| `response_model` 泛型 | 让 OpenAPI 推导出 `data` 的真实 schema；不泛型则退化为 `any` |
| 中间件执行顺序 | `add_middleware` **后注册的先执行** |
| 中间件 vs 依赖 | 基础设施（trace/CORS/日志/限流）用中间件；业务上下文（用户/DB/权限）用依赖 |
| `ContextVar` | 协程级上下文隔离，不串请求；适合 trace_id / 租户 / 数据范围 |
| `pool_pre_ping` | 取连接前先探活，避免数据库重启后连接池全是坏连接 |
| `expire_on_commit=False` | async 场景必须开，否则 commit 后访问属性会触发额外 IO |
| 事务边界 | 放 service 层；crud 只 `flush()` 不 `commit()` |
| `jti` | JWT 唯一 ID，登出时写 Redis 黑名单实现主动失效 |
| 双令牌 | access 短（1h）限风险，refresh 长（7d）免频繁登录 |
| 401 vs 403 | 401 未认证 → 刷新/跳登录；403 已认证无权限 → 只提示 |
| 业务码分段 | 4xxxx 客户端、5xxxx 服务端、1xxxx 起业务域 |
| `@app.exception_handler(Exception)` | **捕获不到中间件内的异常**（ServerErrorMiddleware 在最外层） |
| 4xx/5xx 日志级别 | 4xx 记 warning（预期内），5xx 记 error + 堆栈（需告警） |
| 单飞刷新 | 把刷新 Promise 缓存，多个 401 复用同一 Promise，避免打爆刷新接口 |
| `{ ...to, replace: true }` | `addRoute` 后需重新触发导航才能命中新路由 |
| 兜底 404 | 必须在动态路由之后注册，否则通配路由先匹配 |
| `v-permission` | 用 DOM 移除而非 `display:none`（后者可被改样式恢复） |
| 前端权限的定位 | 体验层，可被绕过；**安全边界在后端** |
| OpenAPI → TS | FastAPI 天然产出规范，`openapi-typescript` 自动生成类型，消灭字段漂移 |
| SQLAlchemy 事件 | `do_orm_execute` + `with_loader_criteria` 可替代 Java AOP 做数据权限 |
| 雪花 ID 传输 | 必须用字符串，JS `Number` 安全上限 2^53-1 会溢出 |

## 二、自测题库

### A. Python 与异步基础（W1）

> **❓ 问题：- A1. `async def` 和 `def` 声明的路由，FastAPI 分别怎么处理？各适合什么场景？**
> `def` 路由会被 FastAPI 丢到 anyio 的工作线程池里执行，不阻塞事件循环；
> `async def` 直接在事件循环中执行。
>
> 选择标准看**你调用的东西是同步还是异步**：
> - 用异步库（`httpx.AsyncClient`、`asyncpg`）→ `async def`
> - 用同步阻塞库（`requests`、`psycopg2`、`boto3`）或 CPU 密集 → `def`（让 FastAPI 帮你丢线程池）

> **❓ 问题：- A2. 为什么不能在 `async def` 路由里调用 `requests.get()`？**
> `requests` 是同步阻塞库，调用时会**阻塞整个事件循环**。
> 结果是：这个请求在等网络 IO 期间，其他所有并发请求都无法被处理——单进程退化成串行。
>
> 正确做法二选一：换成 `httpx.AsyncClient`，或者把路由声明为 `def`。

> **❓ 问题：- A3. `ContextVar` 为什么比全局变量安全？**
> `ContextVar` 的值是按**执行上下文（协程任务）隔离**的。
> 每个请求在独立的 asyncio Task 里执行，各自持有自己的副本，因此不会出现请求 A 的 trace_id 被请求 B 读到的情况。
>
> 注意：`BackgroundTasks` 和线程池任务**不会自动继承** context，需要显式传值。

> **❓ 问题：- A4. `@computed_field` 和普通 `@property` 在 Pydantic 里有什么区别？**
> `@property` 只是 Python 层的属性访问，**不会出现在 `model_dump()` 和 JSON schema 里**。
> `@computed_field` 会让该属性参与序列化，出现在 `model_dump()` 输出和 OpenAPI schema 中。
>
> 典型用途：`emails_enabled`（由 `SMTP_HOST` + `EMAILS_FROM_EMAIL` 派生）这种"派生配置"。

> **❓ 问题：- A5. `model_validator(mode="after")` 和 `field_validator` 怎么选？**
> - `field_validator`：校验**单个字段**，能拿到字段原值
> - `model_validator(mode="after")`：校验**跨字段关系**，拿到的是已构建好的整个模型
>
> 例：「生产环境不允许 `APP_DEBUG=True`」是跨字段关系 → 必须用 `model_validator`。

### B. FastAPI 核心机制（W2）

> **❓ 问题：- B1. FastAPI 的依赖"缓存"到底缓存什么？作用域多大？**
> 缓存的是**依赖函数的返回结果**，作用域是**单个请求**。
>
> 同一请求内，如果多个地方 `Depends(get_current_user)`，函数只会执行一次，后续复用同一结果。
> 请求结束缓存即失效，不会跨请求。
>
> 实际意义：`get_current_user` 可以被鉴权依赖、业务依赖、日志依赖同时引用，而不必担心重复查库。

> **❓ 问题：- B2. `yield` 依赖里 `yield` 之后的代码什么时候执行？**
> 在**响应发送之后**执行（由 Starlette 的依赖清理机制驱动）。
>
> 这意味着：如果依赖的清理逻辑必须"在请求彻底结束前完成"（例如提交事务、释放分布式锁），
> 依赖 `yield` 的时机可能不合适，应该改用 `BackgroundTasks` 或中间件。

> **❓ 问题：- B3. 为什么推荐 `Annotated[X, Depends(...)]` 而不是 `x: X = Depends(...)`？**
> 四个理由：
> 1. **类型信息完整**：IDE 能推导出 `x` 是 `X`，而默认值写法常被推断为 `Any`
> 2. **可复用**：`SessionDep = Annotated[Session, Depends(get_db)]` 可在几十处签名里复用
> 3. **可覆盖**：`app.dependency_overrides[get_db]` 直接替换，测试无需 mock 全局对象
> 4. **默认值位置留给真实默认值**，不会和依赖声明混在一起

> **❓ 问题：- B4. 为什么 `ResponseModel` 必须是泛型？**
> FastAPI 通过 `response_model` 的**类型参数**生成 OpenAPI schema。
> 如果写 `ResponseModel`（非泛型），`data` 字段的类型是未知的，schema 里会变成 `any`。
>
> 后果：前端用 `openapi-typescript` 生成的类型里，所有接口的 `data` 都是 `any`，
> **类型自动生成的价值直接归零**。

> **❓ 问题：- B5. `generate_unique_id_function` 为什么必须定制？**
> FastAPI 默认用「函数名 + 路径 + 方法」拼 operationId，例如
> `read_users_api_v1_system_users_get`。
>
> 前端据此生成的 SDK 函数名会极其冗长且脆弱（路径一改就全变）。
> 定制成 `f"{tag}-{route.name}"` 后，函数名稳定可读，如 `system-users-list`。

> **❓ 问题：- B6. 中间件和依赖，分别适合处理什么？**
> | | 中间件 | 依赖 |
> |---|---|---|
> | 作用范围 | 所有请求（含未匹配路由） | 仅声明了它的路由 |
> | 能否感知路由 | 需自己解析 | 天然有 |
> | 典型用途 | trace_id、CORS、GZip、访问日志、限流 | 当前用户、DB session、分页、权限 |
> | 可测试性 | 较难（全局） | 易（可 override） |
>
> **判断标准**：横切**基础设施**用中间件；**业务上下文**用依赖。

### C. 分层与统一约定（W3）

> **❓ 问题：- C1. 为什么事务边界放在 service 而不是 crud？**
> `crud` 只负责**单表**的原子操作，而一个业务操作通常要写多张表。
> 事务边界应该覆盖"一个完整业务语义"，这个语义只有 `service` 知道。
>
> 如果事务放 crud，一个业务操作会被拆成多个独立事务，
> 中途失败就会出现"用户建了但角色没绑"的脏数据。

> **❓ 问题：- C2. 4xx 记 warning、5xx 记 error，这个区分有什么实际意义？**
> 这是**告警系统能否工作**的前提。
>
> - 4xx 是**预期内**的客户端错误（密码错、参数错、无权限）。用户输错密码不该半夜叫醒运维。
> - 5xx 是**服务故障**，必须带堆栈记 error 并触发告警。
>
> 如果把 4xx 也记成 error，告警会被噪声淹没；反过来，5xx 记成 warning 会漏报。

> **❓ 问题：- C3. 生产环境的错误响应里，为什么只回传 trace_id 而不回传堆栈？**
> 堆栈会泄漏：文件路径、依赖库版本、表名与字段名、甚至局部变量值（loguru 的 `diagnose=True` 会打变量值，可能含密码）。
>
> 正确做法：响应只给 trace_id，用户报障时凭 trace_id 在日志系统里捞完整堆栈。
> 这既保证了可排查性，又不泄漏内部结构。

> **❓ 问题：- C4. 校验失败（422）时，为什么要把 `errors` 数组返回给前端？`loc` 的首段为什么要剥掉？**
> 返回 `errors` 数组让前端能**精确定位到表单字段**并高亮，而不是只弹一句"参数错误"。
>
> `loc` 形如 `("body", "username")` 或 `("query", "page")`，首段是参数来源位置。
> 前端只关心字段名 `username`，所以剥掉首段。

> **❓ 问题：- C5. `@app.exception_handler(Exception)` 能捕获中间件里抛出的异常吗？**
> **不能。**
>
> Starlette 的中间件栈最外层是 `ServerErrorMiddleware`，
> 它位于 `ExceptionMiddleware`（也就是 `app.exception_handler` 生效的地方）之外。
> 中间件内的异常在到达 `ExceptionMiddleware` 之前就被 `ServerErrorMiddleware` 拦下了。
>
> 所以中间件内部必须自己 `try/except`，记录日志后决定是重新抛出还是返回统一结构。

### D. 鉴权与权限（W4）

> **❓ 问题：- D1. JWT 是无状态的，"登出"到底怎么实现？**
> 给每个 token 加 `jti`（唯一 ID），登出时把 `jti` 写进 Redis 黑名单，
> TTL 设为该 token 的**剩余有效期**（过期自动清理，不会无限增长）。
>
> 校验时先查黑名单，命中即拒绝。
>
> 代价：从"完全无状态"变成了"依赖 Redis"。这是安全性与架构简洁性之间的必然取舍。

> **❓ 问题：- D2. 为什么 access token 要短、refresh token 要长？**
> - **access 短（1 小时）**：它随每个请求发送，暴露面大。短有效期限制泄露后的可用窗口。
> - **refresh 长（7 天）**：只在换令牌时使用，暴露面小。长有效期避免用户频繁登录。
>
> 前端在 401 时用 refresh 换新 access，用户无感。**体验与安全由两个令牌分别承担。**

> **❓ 问题：- D3. 前端已经做了按钮级权限，后端为什么还要做接口级权限？**
> 因为**前端权限完全可被绕过**：改 JS、用 Postman 直调、改路由。
>
> - 前端权限 = **体验层**（不该显示的功能别显示）
> - 后端权限 = **安全边界**（唯一真正生效的一层）
>
> 两者的前提是**共用同一套权限码**（`system:user:create`），
> 这样前端隐藏按钮、后端拦截接口，语义一致，不会出现"按钮在但接口拒绝"的错配。

> **❓ 问题：- D4. 401 和 403 在前端应该怎么区别处理？**
> - **401**：不知道你是谁 → 用 refresh 换令牌，失败则跳登录页并记录 `redirect`
> - **403**：知道你是谁但你没权限 → **只提示"无权限"，绝对不要跳登录页**
>
> 把 403 也跳登录页是最常见的体验事故：用户明明登录着，点了个没权限的按钮就被踢出去了。

> **❓ 问题：- D5. 权限码为什么要从数据库聚合 + Redis 缓存，而不是写死在代码里？**
> 写死（如 `if user.role == "admin"`）的问题：
> 1. 角色会变、权限会调，每次都要改代码发版
> 2. 无法支持"运营在后台给角色加权限"
> 3. 权限点一多，代码里全是硬编码分支
>
> 正确做法：用户-角色-菜单-权限码存库，登录后聚合到 Redis，
> **权限变更时主动 `DEL` 缓存**保证一致性。
>
> 但"超管"可以用通配 `*:*:*` 直接放行，不必把几百个权限码塞进数组。

### E. 数据层与横切设施（W5）

> **❓ 问题：- E1. `pool_pre_ping=True` 解决什么问题？**
> 解决**陈旧连接（stale connection）**问题。
>
> 数据库重启、网络闪断、或中间件（如 PgBouncer）超时断开后，
> 连接池里仍持有已失效的连接。此时拿到的连接一用就报错。
>
> `pool_pre_ping` 会在从池中取连接前先发一个轻量探活（通常是 `SELECT 1`），失败则丢弃并重建。
> 代价是每个连接多一次往返，但换来的是稳定性——**生产环境必开**。

> **❓ 问题：- E2. 中间件的注册顺序和执行顺序为什么是反的？**
> Starlette 的中间件是**洋葱模型**：`add_middleware` 每次把新中间件包在已有栈的**外层**。
> 所以最后注册的最先接触到请求，也最后接触到响应。
>
> 实践含义：
> - 想让某个中间件覆盖**所有**请求（如 Trace），就要**最后** `add_middleware`
> - CORS 通常也要靠外层，否则预检请求可能被内层拦截

> **❓ 问题：- E3. `expire_on_commit=False` 在 async 场景为什么必须开？**
> 默认 `True` 时，`commit()` 会让 session 里的对象**过期**，
> 之后访问任何属性都会触发一次新的数据库查询来刷新。
>
> 在 async 场景下这会引发两个问题：
> 1. 隐式 IO，且发生在 `await` 之外，可能抛 `MissingGreenlet` 错误
> 2. 典型的 N+1 查询
>
> 设为 `False` 后，commit 不使对象过期，属性可直接读取。

> **❓ 问题：- E4. 什么是 N+1 查询？怎么在 SQLAlchemy 里避免？**
> 查出 N 条主记录后，访问每条记录的关联对象时各发一次查询，总共 N+1 次 SQL。
>
> 解决：用显式预加载
> - `selectinload(Model.relation)` —— 单独一条 `IN` 查询，适合一对多
> - `joinedload(Model.relation)` —— JOIN 一次取回，适合多对一
>
> 关键：**不要依赖惰性加载**，在查询时就声明清楚要加载什么。

> **❓ 问题：- E5. trace_id 怎么做到"从浏览器一次点击关联到数据库一条 SQL"？**
> 三个环节：
> 1. **前端**：请求拦截器生成 `X-Request-Id` 并注入请求头
> 2. **后端中间件**：读取该头（没有则生成），写入 `ContextVar` 与 `request.state`，并回写到响应头
> 3. **日志**：loguru 的 `patcher` 给每条日志注入 `extra.trace_id`
>
> 这样前端报障时给出响应头里的 trace_id，就能在日志系统里捞出这个请求的全部日志（含 SQL）。
>
> 这是**投入产出比最高的可观测性改造**——代码量极小，排查效率提升极大。

> **❓ 问题：- E6. 数据库唯一索引冲突，应该返回 500 还是业务错误？**
> 必须返回**业务错误**（如 400 + "数据已存在"）。
>
> 唯一索引冲突是**可预期的业务场景**（用户重复提交、并发创建同名资源），
> 不是服务故障。返回 500 会让前端无法区分"重试就好"和"服务挂了"，
> 也会污染告警系统。
>
> 实现：注册 `IntegrityError` 的 exception handler，把 `exc.orig` 记入日志（含约束名），
> 响应只回传友好文案。

### F. 前端工程化（W6）

> **❓ 问题：- F1. 401 并发时如果不做单飞，会发生什么？**
> 假设页面同时发了 5 个请求，access token 都过期了。
> 5 个请求各自收到 401，各自去调刷新接口 → **刷新接口被并发打 5 次**。
>
> 如果刷新接口有"旧 refresh token 用后失效"的机制，
> 后 4 次刷新会失败，用户被强制登出。
>
> **单飞（single-flight）**：把刷新 Promise 缓存在模块级变量里，
> 第一个 401 负责真正刷新，其余复用同一个 Promise，刷新完成后统一重放。

> **❓ 问题：- F2. `router.addRoute` 之后为什么必须 `return { ...to, replace: true }`？**
> 因为在守卫执行的那一刻，当前导航的目标路由**还没被注册**，
> 直接 `return true` 会让这次导航按旧路由表匹配，结果命中 404 或白屏。
>
> 返回 `{ ...to, replace: true }` 会**中断当前导航并重新发起一次**，
> 此时新路由已注册，就能正确匹配。
>
> `replace: true` 是为了不产生一条无意义的历史记录（否则用户按返回键会卡在中间态）。

> **❓ 问题：- F3. 兜底 404 路由为什么必须最后注册？**
> 兜底路由是 `path: '/:pathMatch(.*)*'` 这样的**通配**路由。
> 路由匹配是按注册顺序的，通配路由一旦注册在前，会**吃掉所有后续动态路由**。
>
> 所以顺序必须是：静态路由 → 动态路由（`addRoute`）→ 兜底路由。

> **❓ 问题：- F4. 为什么 token 要持久化，而 permissions 不要持久化？**
> - **token 持久化**：刷新页面后要能继续用，否则每次都跳登录
> - **permissions 不持久化**：权限是**服务端状态**。如果缓存在本地，
>   管理员刚收回了某个权限，用户前端仍然显示该按钮，直到缓存过期——这是**安全与体验双重问题**
>
> 正确做法：刷新页面时用 token 重新拉一次用户信息和权限。

> **❓ 问题：- F5. `v-permission` 为什么用 DOM 移除而不是 `display: none`？**
> `display: none` 只是视觉隐藏，用户可以在 DevTools 里改样式恢复按钮，甚至直接调接口。
>
> DOM 移除让元素不存在于文档树中，恢复成本更高。
>
> 但必须强调：**这两种都不是安全边界**。真正的安全在后端接口权限。
> 前端做这一层只是为了不让用户看到"点了会失败"的按钮。

> **❓ 问题：- F6. `openapi-typescript` 这条链路的价值到底在哪？**
> 它解决的是**前后端字段漂移**这个最耗时的联调问题。
>
> 传统流程：后端改字段 → 前端不知道 → 运行时才发现 → 排查 → 修 → 再测。
> 自动生成流程：后端改字段 → CI 重新生成类型 → **前端构建失败** → 编译期就暴露。
>
> 关键前提是后端 `response_model` 必须是泛型且标注完整，
> 否则生成的类型全是 `any`，这条链路就白做了。

### G. 跨栈思维与架构判断（W7）

> **❓ 问题：- G1. Java 的 `@Transactional`，在 FastAPI 里怎么等价实现？**
> 两条路：
> 1. **显式事务（推荐）**：在 `service` 层用 `async with self.db.begin():` 包住多表操作
> 2. **装饰器**：自己写一个 `@transactional()` 装饰器，内部 `async with self.db.begin()`
>
> 关键约定：`crud` 层只 `flush()` 不 `commit()`，事务完全由 `service` 控制。
>
> Python 没有注解式 AOP 的天然土壤，**显式化反而更容易调试**（堆栈清晰、没有魔法）。

> **❓ 问题：- G2. Spring AOP 的日志切面，在 FastAPI 里用什么替代？**
> 分两类，用不同手段：
> - **基础设施类**（访问日志、耗时、trace）：用**中间件**，一次覆盖所有请求
> - **声明式语义类**（"记录这次删除操作"）：用**装饰器**，写在路由函数上
>
> 装饰器有两个坑：
> 1. 必须放在 `@router.get()` **下面**（先被路由装饰器拿到真实函数）
> 2. 必须用 `@wraps` 保留签名，否则 FastAPI 的参数解析会失效

> **❓ 问题：- G3. 数据权限（不同部门看不同数据）怎么实现？为什么不在每个查询里手写条件？**
> 手写 `where(dept_id.in_(...))` 的问题：**一定会漏写**。几十个查询里漏一个就是数据泄漏。
>
> 正确做法：用 SQLAlchemy 的 `do_orm_execute` 事件 + `with_loader_criteria`，
> 在 SQL 执行前统一追加过滤条件；数据范围从 `ContextVar` 读取（鉴权依赖写入）。
>
> 这正是 Java 用 AOP 改写 SQL 想达到的效果，而 SQLAlchemy 的事件机制天然支持。

> **❓ 问题：- G4. 你为什么**没有**上插件化 / 多租户？（考判断力）**
> 参考答案的骨架：
>
> 1. **先问需求**：插件化服务的是"客户按套餐启用模块"，多租户服务的是"SaaS 化"。
>    如果没有这两类真实需求，它们只是复杂度。
> 2. **成本**：插件化会引入"运行时才能发现的问题"（依赖冲突、加载顺序、配置来源）；
>    多租户要么改所有表的查询（字段隔离），要么动部署架构（schema/库隔离）。
> 3. **替代方案**：模块注册器（L2 境界）能拿到 80% 的组织收益，成本是插件化的 10%。
> 4. **结论**：等真实需求出现再上，架构要为变化留口子，但不为想象买单。
>
> 这题考的不是"你会不会"，而是"你知不知道自己为什么不做"。

> **❓ 问题：- G5. FastAPI 生态为什么没有 Vue 那样的 20k+ star 后台框架？这对选型意味着什么？**
> 三个原因：
> 1. **定位差异**：FastAPI 官方定位是"框架"（framework），不是"脚手架"（boilerplate），官方明确不做业务层
> 2. **社区形态**：Python 后端更多是**服务化/API 化**场景，而非"后台管理系统"这一特定品类；
>    Vue 生态的高星项目几乎全是 admin template，需求高度同质化
> 3. **碎片化**：认证、权限、代码生成各有独立库，没有形成"全家桶"共识
>
> **选型含义**：选 FastAPI 意味着你要自己组装企业级能力（异常体系、统一响应、RBAC、可观测性）。
> 好处是每一层都可控、无框架绑架；代价是前期投入更大，需要有人懂架构。
> 反过来说，这也正是"懂架构"的工程师在 FastAPI 项目里的价值所在。

> **❓ 问题：- G6. 如果用一句话概括「Java 的做法怎么落到 Python」，你会怎么说？**
> **Java 用注解和 AOP 做的事，Python 用「显式依赖 + 上下文变量 + 装饰器」做。**
>
> - 横切的**基础设施**（trace、租户、日志）→ 中间件 + `ContextVar`
> - 横切的**业务上下文**（用户、DB、权限、分页）→ `Depends` 依赖
> - 横切的**声明式语义**（事务、操作日志）→ 装饰器 + `@wraps`
>
> 三条路覆盖了 Spring AOP 的绝大部分使用场景，而且比 AOP **更容易调试**。
